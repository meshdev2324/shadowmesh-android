### The shape change, not a type change

The old fixture populated `endpoint` and `publicKey` — the connect material the
anonymous projection withholds (L10, F59). `MeshNodeEntry`
(`core/vpn/.../NodeDirectory.kt:43-63`) **has no such fields and did not gain
any.** The only way to make the old fixture compile was to widen the projection
and re-admit the credentials it exists to withhold, which L10 explicitly
overruled. So the assertion changed shape:

| assertion | before | after |
|---|---|---|
| what the fixture carries | endpoint + publicKey + load + latency | `id`, `country`, `region`, `isOnline` |
| what the row is asserted to be | node identity | **geography**: `"United States • San Francisco • CHECKING"` |
| what is asserted absent | *(nothing)* | any `:51820` port or `pubkey` token, anywhere in the sheet |
| selection check | `kotlin.assert` (compiled out without `-ea`) | JUnit `assertNotNull`/`assertEquals` |

The `CHECKING` word is the honest pre-stage-2 value: the directory withheld the
endpoint, so whether a node serves REALITY is unknown. `DIRECT` would be a
confident label with no evidence behind it.

The port/key assertions are the pin. They are what go red if anyone widens
`MeshNodeEntry` to resurrect the old fixture.

## Item 3 — F67 — branch taken: **REMOVED**, not relabelled

Removed `SpeedResultItem("Latency", …)` from the speed-test row. The branch
that does **not** wait on L9's rename, which is the point: the trap was that

### The site is not the field L9 is renaming

`r` is `uniffi.shadowmesh.SpeedTestResult`, so this bound
`SpeedTestResult.latency_ms` (`speed_test.rs:22`, `f64`) — **not**
`NetworkReport.latency_ms` (`detector.rs:29`, `u32?`). Both are a mean of 5
`speedtest_ping` calls; `speedtest_ping_async` (`api_client.rs:1367-1377`) is a
full HTTP round-trip to the control-plane edge, timed with `Instant::now()`.

So L9's rename **does not reach this site**. It would compile and render
unchanged, leaving a bare "Latency" that *looks* fixed — the F59 nine-site drift
mechanism exactly.

`SpeedResultContractTest` pins this in the source set CI actually runs, because
`core/ui`'s instrumented tests are compiled but never run. **Proved
non-vacuous:** re-adding the latency row turns 3 of its 4 tests red
(`renders no bare Latency label`, `binds no latency property`,
`no bare noun`), and the 4th correctly stays green because Download survived.

### The safety question

> *For a censorship-circumvention tool, what should the connected surface claim
> when it cannot measure what the label implies?*

**It should claim the thing it can actually observe, and refuse the rest.**

The connected surface has exactly one thing it knows for certain: **is traffic
routed, or not.** That is a binary the tunnel itself produces, and it is what
the orb already says ("Protected. Traffic is routed through the mesh.").

Latency is not that. It is a measurement *of a measurement* — five HTTP
round-trips to the one host an adversary is most motivated to slow, throttle,
or impersonate. Under duress that is the figure most likely to be wrong **in
the reassuring direction**: a far-away edge reads high while the tunnel is
fine, and a genuinely degraded tunnel can read fine. A user under surveillance
making a safety decision from that number is making it on the one input the
adversary controls.

So: **an absent figure is honest; a wrong-but-reassuring figure is worse than
none, because it gets acted upon.** That is the whole reason this was removed
rather than renamed to "API Latency".

This is a floor, not a preference — and it cuts the same way on the connected
surface as L10's floors do. Note it is *not* "hide the bad news": Download and
Upload stay, because throughput over the path in use is actionable, and
`packet_loss`/`is_connected` keep their full denominator per L9's F68 fix. The
line is not optimism vs. pessimism. It is **a claim must name what produced it.**

### Read-out contract for L9 (it is blocked on this)

L9's UDL comment says the rename "requires L7's read-out contract (F52/F67)".
It is here, and it is short:

1. `NetworkReport.latency_ms` has **zero display consumers** in the Android
   client. Verified: Diagnostics renders Connection, Type, DPI Status, Server
   Heuristic, Portal, Mesh Advice — and has no latency, jitter or packet-loss
   row (`ShadowMeshComponents.kt:2137-2181`). **The rename is therefore a no-op
   in this tree, not a call-site sweep.**
2. A comment at `StatusScreen.kt:183` previously asserted the opposite ("still
   shown in Network Diagnostics") on a premise that had quietly gone false.
   Corrected — it was a trap, since it read as licence to resurface the figure.
3. When the rename lands, bind it and label it `control_plane_rtt_ms` /
   "Control plane RTT", and show it **only** on an explicit measurement surface
   that already names its subject. Never on the orb, never as a bare noun.
4. Read it **with `packet_loss`**. F68 made the latency floor at two samples
   while `packet_loss` keeps all five, so the two now disagree about the same
   denominator by design. A RTT row shown without the loss beside it is the
   original defect one level down.

## Item 4 — FLAG_SECURE

**`isScreenshotEnabled` default = `false` (secure).** Two independent defaults,
both secure:
- `VPNUiState.kt:90` — `val isScreenshotEnabled: Boolean = false`
- `VPNManagerViewModel.kt:400` — `prefs.getBoolean(Config.KEY_SCREENSHOTS_ENABLED, false)`

**L10's reading of the gate is confirmed correct** (`MainActivity.kt:99-102`):

```kotlin
val isSensitiveScreen = uiState.showMfaSetup || !uiState.isActivated || uiState.isSecurityLockEnabled
if (isSensitiveScreen || !uiState.isScreenshotEnabled) addFlags(FLAG_SECURE) else clearFlags(FLAG_SECURE)
```

The orchestrator's assertion that it was ungated was wrong; it had not been read.

### Verdict: the default is right, the form is under-scoped

Not implemented here — L6/L10's call, and L10 rules permanently-*on* the wrong
way, so this is raised not actioned.

**What holds.** Secure by default, on a fresh install and on every launch. The
floor survives a process death and an app update, because it is re-derived from
state rather than remembered. A user who never touches the toggle is covered.

**What does not hold.** The toggle is **global and persistent**. One moment of
curiosity — "let me screenshot this" — writes `screenshots_enabled=true`
(`VPNManagerViewModel.kt:1185`) and `FLAG_SECURE` is then cleared for **every**
subsequent non-sensitive launch, indefinitely, with no re-prompt, no time-box
and no auto-re-arm.

And the predicate that guards it does not know what is on screen.
`isSensitiveScreen` is about *session* state (MFA pending, not activated,
lock enabled). It is not a test for *content*. So on a fully-configured app with
no PIN, the node list, the diagnostics panel and every settings screen are all
"non-sensitive", and the user's single toggle exposes all of them at once.

Concretely, against L10's floor — *"recents must not disclose a node list"* —
the floor rests **entirely** on `FLAG_SECURE` blanking the recents thumbnail.
There is no second line of defence:
- `android:excludeFromRecents` appears **nowhere** in
  `app/src/main/AndroidManifest.xml`. The two hits in the merged manifests come
  from third-party libraries (`play-services-auth`'s `SignInHubActivity`,
  LeakCanary's `RequestPermissionActivity`) and are not ours.
- `android:visibility` / `VISIBILITY_SECRET` is never set.
- `setRecentsScreenshotEnabled(false)` (API 33+) is never called — this is the
  purpose-built API for exactly this and is unused.

So one toggle flip silently disarms the only mechanism protecting the floor.

**Recommendation (L6 + L10, not L7).** Scoping options, roughly in cost order:
`setRecentsScreenshotEnabled(false)` unconditionally as a second layer;
`excludeFromRecents`/task-hide on the node-list surface; and time-boxing or
re-prompting the opt-in so it cannot be left on indefinitely. All three touch
shared visual/behaviour surfaces and none are L7's to land alone.
